# FPL Draft H2H Analytics

A Streamlit dashboard for analysing an FPL Draft head-to-head league beyond the standard league table.

The app uses the FPL Draft and Fantasy Premier League APIs to combine gameweek scores, fixtures, draft choices, transactions, historical squads, player scores, and counterfactual schedule analysis.

The default league ID is **48609**, but the app can be used with another compatible FPL Draft league.

## Features

### Gameweek Scores

- Current H2H league table
- Gameweek scores for every participant
- Gameweek finishing positions
- Actual and expected H2H performance

### 5-GW Periods

Breaks the season into five-gameweek periods so short-term performance can be compared without relying only on the full-season table.

### H2H

- Head-to-head records
- Fixture history
- Matchup comparisons
- Close games and opponent-related analysis

### League Analysis

League-wide performance analysis, including:

- Best and worst gameweeks
- Consistency
- Position contribution
- Counted points by `GK`, `DEF`, `MID`, and `FWD`
- Points per played positional slot
- Most-played formations

`Pts/played slot` measures the points generated by a position divided by the number of counted lineup slots used at that position. For example, midfielder points are divided by the total number of midfielders that actually counted in the manager's final XIs.

### Schedule Analysis

Analyses how much the H2H fixture draw affects the standings while keeping every participant's real gameweek scores unchanged.

The app **exhaustively enumerates all 720 possible fixture-slot assignments (6!)**. This is not a Monte Carlo simulation or a sample.

`Average` is treated as the sixth schedule participant, matching the league's actual fixture structure.

The section includes:

- **Schedule summary** — actual H2H points compared with the distribution across all 720 schedules, including mean, median, minimum, maximum, and percentile
- **Finishing-position distribution** — how often each participant finishes 1st through 6th across all schedules
- **All-season H2H matrix** — the W-D-L record each row participant would have against each column participant if they played one another every completed gameweek
- **Alternative schedule explorer** — inspect valid alternative fixture draws and their resulting standings

The schedule analysis changes only the fixture draw. It never changes the scores managers actually recorded.

### Squad Activity

Tracks squad-management decisions through waivers and free agents.

- Activity summary by manager
- Successful and failed waivers
- Contested waiver analysis
- Completed squad changes
- Cumulative waiver/free-agent impact

The cumulative transaction analysis compares actual results with counterfactual no-move scenarios. It includes both a direct replacement interpretation and an adjusted interpretation that accounts for plausible bench alternatives rather than automatically assuming a transferred-out player would have started.

### Player Performance

Player-level analysis based on historical Draft squads and live FPL player scores.

- **Player contribution** — starts, counted appearances, autosubs, counted points, and ownership spells
- **Acquisition impact** — performance during each waiver/free-agent ownership spell
- **Transaction comparison** — player-in versus player-out performance after a move
- **Short-stay returns** — productive brief acquisitions
- **Painful drops** — performance after a player was released and subsequently acquired
- **Former players against their old manager** — H2H returns after a move
- **Draft performance** — performance from the original draft ownership spell only
- **Lineup decisions** — bench and lineup outcomes

Ownership is modelled as separate spells, so drafting a player, dropping them, and later reacquiring them does not incorrectly merge the original draft spell with the later acquisition.

### Charts

League-wide visualisations, including:

- Cumulative H2H points
- Cumulative expected H2H points
- Cumulative FPL points
- Distribution of H2H points across all 720 valid fixture schedules

## Data sources

The app currently uses endpoints from the FPL Draft API and the regular FPL API, including:

```text
https://draft.premierleague.com/api/league/{league_id}/details
https://draft.premierleague.com/api/draft/{league_id}/choices
https://draft.premierleague.com/api/draft/league/{league_id}/transactions
https://draft.premierleague.com/api/entry/{entry_id}/event/{gw}
https://fantasy.premierleague.com/api/event/{gw}/live/
```

Player IDs are shared between the Draft and regular FPL APIs.

The FPL Draft API is undocumented and may change without notice. The app therefore uses defensive parsing where practical.

## Run locally

Create a virtual environment and install the project dependencies:

```bash
python -m venv .venv
```

Windows:

```bash
.venv\Scripts\activate
```

macOS/Linux:

```bash
source .venv/bin/activate
```

Then:

```bash
pip install -r requirements.txt
streamlit run app.py
```

## Hosting

The application is suitable for a small Streamlit deployment because it is read-only, does not require a database, and performs relatively lightweight calculations.

A simple deployment can use **Streamlit Community Cloud**:

1. Put `app.py`, `requirements.txt`, and this `README.md` in a GitHub repository.
2. Connect the repository to Streamlit Community Cloud.
3. Select `app.py` as the entry point.
4. Deploy and share the resulting Streamlit URL.

For a small private FPL league, the free Community Cloud tier is a reasonable place to start.

## Performance and caching

The app makes several API requests for historical gameweeks, squads, transactions, and player scores. Streamlit caching should be used for API data that does not need to be fetched on every rerun.

The exhaustive schedule analysis evaluates only **720 schedules**, so it is small enough to calculate directly; no random simulation is necessary.

## Project structure

The application currently keeps most logic in `app.py`. As it grows, a useful future refactor would be:

```text
app.py
fpl_api.py
league_analysis.py
schedule_analysis.py
player_analysis.py
transactions.py
```

This would separate API access, calculations, and Streamlit presentation while preserving the current behaviour.
